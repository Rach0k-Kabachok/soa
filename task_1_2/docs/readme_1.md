## Запуск

```sh
docker build -t marketplace-catalog .
docker run --rm -d --name marketplace-catalog -p 127.0.0.1:18080:8080 marketplace-catalog
curl -i http://localhost:18080/health
```

Ожидаемый ответ:

```http
HTTP/1.1 200 OK
Content-Type: text/plain

ok
```

Остановка:

```sh
docker stop marketplace-catalog
```

Сервис слушает порт `8080`; при запуске в Docker он доступен на порту `18080` компьютера.
Endpoint проверяет, что HTTP-сервер работает; внешних зависимостей у каркаса нет.

## Домены, сервисы и владение данными
Решил выделить 4 сервиса. Как по задани. и сказано, у каждого своя бд, они не разделяются

| Домен | Ответственность | Сервис | Собственные данные |
| --- | --- | --- | --- |
| Пользователи | Учётные записи, роли покупателя и продавца, профили и предпочтения | Users Service | Users DB: аккаунты, роли, профили, предпочитаемые категории |
| Каталог | Управление товарами продавца, категориями, ценами и остатками | Catalog Service | Catalog DB: товары, принадлежность продавцам, категории, цены, остатки и прочее |
| Персонализированная лента | Формирование и упорядочивание доступных товаров | Catalog Service | Собственных дополнительных данных нет; использует свой каталог и предпочтения из Users API |
| Заказы | Оформление заказа, состав и стоимость, жизненный цикл заказа | Orders Service | Orders DB: заказы, покупатель, снимки позиций и цен, статусы |
| Платежи | Расчёт суммы по снимкам заказа, создание платежа у провайдера, учёт результата | Orders Service | Orders DB: платёжные попытки, суммы, идентификаторы провайдера и статусы платежей |
| Уведомления | Отправка покупателю сообщений о статусах заказа | Notifications Service | Notifications DB: обработанные события, сообщения, попытки и результаты доставки |

Тут на всякий случай уточню:
- Хоть и к OrderDb привязаны 2 домена, это все еще один сервис, так что разделения нет
- Персонализированная лента Обращается через Api к UserDB, которая находится в другом сервисе. Но при этом контроля над UserDB у нее нет, она может только запрашивать данные

### По какому принципу разделил домены

- **Пользователи отдельно:** аккаунты, роли и предпочтения используются разными частями платформы и имеют собственный жизненный цикл.
- **Каталог и лента вместе:** лента является выборкой товаров из каталога; отдельный сервис рекомендаций и копия каталога для выбранной персонализации не нужны.
- **Заказы и платежи вместе:** стоимость заказа, платёжные записи и статусы тесно связаны. Их локальные изменения можно сохранять в одной транзакции. Это сокращает число межсервисных взаимодействий; операция у внешнего платёжного провайдера всё равно не входит в транзакцию базы данных.
- **Уведомления отдельно:** задержки и ошибки отправки писем не должны блокировать оформление заказа и обработку платежа.

### Насчет рекомендательнйо системы

Покупатель указывает предпочитаемые категории в профиле. Catalog Service получает их из Users Service и помещает доступные товары этих категорий первыми, внутри групп сортируя по времени добавления. Остальные товары идут следом. При отсутствии предпочтений или недоступности Users Service используется общая лента по времени добавления.

## Кто с кем взаимодействует

| Кто → кому | Способ | Назначение |
| --- | --- | --- |
| Покупатель, продавец → Web App | Синхронно, HTTPS | Работа через веб-интерфейс |
| Web App → Users Service | Синхронно, REST/HTTPS | Учётная запись, профиль, предпочтения |
| Web App → Catalog Service | Синхронно, REST/HTTPS | Каталог, персонализированная лента, управление товарами продавца |
| Web App → Orders Service | Синхронно, REST/HTTPS | Оформление заказа, начало оплаты, просмотр статуса |
| Catalog Service → Users Service | Синхронно, REST/HTTPS | Получение предпочтений покупателя |
| Orders Service → Catalog Service | Синхронно, REST/HTTPS | Получение актуальных цен, резервирование и освобождение остатков |
| Orders Service → платёжный провайдер | Синхронно, REST/HTTPS | Создание платежа на рассчитанную сумму |
| Платёжный провайдер → Orders Service | Асинхронный результат через webhook, HTTPS | Результат платежа; приходит позже, отдельно от запроса создания платежа |
| Orders Service → Notifications Service | Асинхронно для бизнес-процесса, REST/HTTPS | Фоновая доставка `OrderStatusChanged` из outbox; `202 Accepted` после сохранения события |
| Notifications Service → почтовый провайдер | Синхронно, REST/HTTPS | Отправка уведомления покупателю |
| Каждый сервис → собственная PostgreSQL DB | Синхронно, PostgreSQL protocol/TCP | Чтение и запись принадлежащих сервису данных |

## Альтернативы и финальный выбор

| Вариант | Разбиение | Плюсы | Минусы |
| --- | --- | --- | --- |
| A. Модульный монолит | Один backend с модулями пользователей, каталога/ленты, заказов/платежей и уведомлений; одна принадлежащая ему PostgreSQL DB | Проще запуск и сопровождение; локальные вызовы; заказ, платёжные записи и остатки можно изменять в одной транзакции | Масштабируется и выпускается целиком; ошибка в процессе может затронуть все домены; медленная отправка уведомлений требует изоляции фоновой работы внутри приложения |
| B. Четыре сервиса | Users, Catalog с лентой, Orders с платежами, Notifications; четыре собственные PostgreSQL DB | Каталог и уведомления масштабируются и выпускаются независимо; ошибки почтовой интеграции изолированы; владение данными закреплено за сервисами | Больше процессов и инфраструктуры; сетевые вызовы могут завершаться ошибкой; резервирование остатков требует компенсации, а фоновая доставка событий — диспетчера, повторов и идемпотентности |

## Почему выбрал второй вариант. ##

В основном из-за независимости компонентов и простоты машстабирования относительно первого варианта. Первый вариант был бы легче, но, если мы начнем упираться в предел произвоидетльности одного модуля, то расширить горизонтально его не сможем. А тут у нас есть и блочность, и изоляция

Backend-сервисы спроектированы на Go с `net/http`, базы — PostgreSQL, веб-приложение — React. Это приблизительный стек, я не знаю, каким он будет на самом деле, но из того, что я прочитал про C4 container, не упомянуть это я не мог
